# CodeTape 部署、备份与迁移

本版使用单实例 Node.js 24、SQLite 和私有磁盘对象。账号、会话、协作文档、录制元数据、分享与上传状态在同一个 SQLite 数据库中；媒体和其他录制资产在私有 `objects` 目录。本文补充功能升级 Spec 的部署和恢复流程，产品范围仍以 PRD、技术方案为准。

## 1. 部署配置

先使用锁定依赖完成安装、Schema/API/Web 构建以及相关测试。`better-sqlite3`、Argon2 是原生依赖，镜像和实际运行环境必须使用兼容的 Node.js 24 与系统架构，不能复制另一操作系统生成的 `node_modules`。

| 配置                        | 用途                                                                         |
| --------------------------- | ---------------------------------------------------------------------------- |
| `NODE_ENV=production`       | 启用生产 Cookie 策略；禁止测试故障开关                                       |
| `CODE_TAPE_DATA_DIR`        | 持久数据目录，例如 `/srv/codetape-data`，不能放在公开 Web 根目录             |
| `CODE_TAPE_AUTH_SECRET`     | 至少 32 字节的稳定服务端签名密钥，由 Secret Manager 注入；缺失时生产拒绝启动 |
| `CODE_TAPE_PUBLIC_BASE_URL` | 实际 HTTPS 站点地址，与反向代理和 Web origin 一致                            |
| `CODE_TAPE_ALLOWED_ORIGINS` | 明确的可信 Origin 列表，不使用通配 credentials CORS                          |
| `CODE_TAPE_WEB_ROOT`        | Web 生产构建目录，例如 `apps/web/dist`                                       |
| `HOST` / `PORT`             | 内部监听地址和端口，由 HTTPS 反向代理接入                                    |

API 服务账号只拥有数据目录的读写权限；目录采用 `0700`，密钥与备份文件采用 `0600`。SQLite、私有对象与备份都不能作为静态文件对外开放。HTTP GET、HEAD 和 Range 应继续通过受权限校验的资产路由。

首版只启动一个 API 实例。不能直接横向增加多个实例，各自维护同一协作房间却没有共享广播机制；也不能在不同容器里各创建一份临时数据库。

生产需要保持 HTTPS、WebSocket 升级转发和正确的可信 Origin。日志不记录密码、JWT、refresh Cookie、分享 token、资产 grant 或完整代码/字幕正文；访问日志也应隐藏携带 grant 的查询参数。

服务端审计采用白名单 JSON 事件，区分收到更新、SQLite 提交和 ACK 入队；ACK 入队不代表对端已经收到或应用。浏览器排障可在构建时显式设置 `VITE_CODE_TAPE_DEBUG_ENABLED=true`，查看协同更新阶段、录制观察流序号与回放代次；默认关闭，不把代码、字幕或认证材料写入控制台。邀请明文只在创建/重新生成时返回，刷新后由候选人显式生成新邀请，不从数据库找回旧明文。

## 2. 数据布局与备份范围

数据目录包含 `code-tape.sqlite`、私有 `objects/`，开发模式还会保存 `auth-secret`。备份工具通过 SQLite backup API 读取一致快照，并只把新快照切换为单文件 DELETE journal；源数据库不修改，也不直接复制可能遗漏提交内容的主数据库文件。随后复制整个私有对象树以及现存的 `auth-secret`。

这是服务端备份。浏览器 IndexedDB 中尚未上传的本地录制、字幕派生资产和协同离线草稿不在其中；录制可另行导出 ZIP，协同状态应以服务端持久化 ACK 确认是否已经保存。不能把服务器快照当成所有客户端数据的备份。

生产使用外部 `CODE_TAPE_AUTH_SECRET` 时，密钥可能没有保存为数据目录内的文件。工具不会读取或输出环境变量密钥，而是在 manifest 中记录 `authSecretIncluded: false`。这类备份还依赖独立保管的 Secret Manager 版本：迁移时必须注入同一密钥；仅有数据备份不能声称包含完整的凭据配置。

备份目标是一个此前不存在的新目录。工具拒绝覆盖已有目录，并拒绝源与目标互相包含，即不能把备份放进数据目录内部，也不能把数据目录的父目录当作备份目标。符号链接和特殊文件不会被跟随复制。

每份完成的备份含有 `backup-manifest.json` 与 `backup-manifest.sha256`。manifest 记录快照开始时间、完成时间、密钥文件是否包含、每个文件的字节数与 SHA-256。验证还检查 SQLite 的 `quick_check`，以及数据库中已提交的对象是否有匹配大小的实际私有文件。

SHA-256 用于检查文件与 manifest 的完整性，不是数字签名，也不能抵御同时能篡改备份和校验文件的攻击者。备份仍需可信存储、访问限制和离线/异地加密副本；加密密钥应另行保管。

## 3. 停机维护期备份

**必须先停止 API。** SQLite backup API 能给数据库提供一致快照，但不能同时冻结外部对象文件。服务仍在接收上传、校验或清理请求时，数据库与文件可能不处于同一个状态；不能以“SQLite 支持在线 backup”为由省略维护期。

1. 进入维护期，停止接受新上传和协作会话，等待正在提交的请求完成。
2. 正常停止唯一 API 进程及任何会写同一数据目录的任务，确认已退出。
3. 在已有的受限备份父目录内选一个新的目标路径，运行备份并验证。
4. 验证成功后再启动原服务；记录版本、依赖锁、外部密钥版本和备份时间。

```sh
node scripts/data-backup.mjs backup /srv/codetape-data /srv/codetape-backups/2026-10-07-01
node scripts/data-backup.mjs verify /srv/codetape-backups/2026-10-07-01
```

目标父目录必须已存在。成功命令返回操作、目标和快照时间，不输出密钥、账号或对象正文。失败时目标可能保留不完整文件，便于排查；不能仅因为目录或 manifest 存在就认为备份成功，必须检查退出状态和 `verify` 结果。再次尝试应选择新的目标目录。

## 4. 恢复到新目录

保持 API 停止，先验证备份，再恢复到新目录，原数据目录不被修改。

```sh
node scripts/data-backup.mjs verify /srv/codetape-backups/2026-10-07-01
node scripts/data-backup.mjs restore /srv/codetape-backups/2026-10-07-01 /srv/codetape-restored-2026-10-07
```

`restore` 在创建目标前验证备份，复制后再校验文件和数据库关系。校验失败不会修改原数据，也不会把坏备份当成成功恢复；不要启动失败命令留下的目标目录。

先以备份对应的应用版本和依赖启动隔离实例，将 `CODE_TAPE_DATA_DIR` 指向新目录，并恢复相同的外部密钥配置。确认账号数据、受保护资源、协作文档和待校验任务正常后，再切换正式流量。恢复后的房间连接应重新建立；旧 WebSocket 连接 ID 不属于可恢复的持久状态。

恢复较早的备份会回到当时的授权状态。例如，在备份之后撤销的会话、分享或邀请，可能在数据库快照里仍为有效。因此恢复演练可以检查旧 JWT 以证明密钥与数据库确实一致，但生产切流量前必须采用明确的失效策略：撤销恢复出的登录会话、一次性票据、下载 grant 和旧邀请；若无法核对备份后发生的分享撤销，也应统一撤销恢复出的分享链接，并让 owner 重新创建。还要核对账号禁用和房间成员变更；无法确认授权的旧房间保持关闭，由候选人重新建立。强制重新登录不能替代这些授权核对。会话和资源撤销按服务端 API/维护流程操作，不只清浏览器 UI。

数据目录变更与应用回滚分开处理。保留原目录；确认新目录成功运行后再安排原目录归档，不在恢复步骤里删除原数据。不要通过恢复旧匿名认证接口作为回滚手段。

## 5. Schema 与旧数据迁移

升级前保留可验证的停机备份，数据库结构优先添加式修改。`0.1.0` 录制先按原版本校验结构与原始 checksum，再迁移到 `0.2.0` 播放结构；不能重算 checksum 后把损坏数据当作合法旧包。原始 ZIP 保留不变，重新导出才生成新版本。

旧匿名设备 token 不能作为云端 owner 身份证明。没有可靠、预登记的服务端迁移凭据时，应保留本地 ZIP，再由登录用户明确上传；旧云端数据认领必须通过可信核实，不因为提交旧 ownerId 就转移所有权。

三个前端发布开关默认开启：`VITE_CODE_TAPE_COLLABORATION_ENABLED`、`VITE_CODE_TAPE_EVENT_TIMELINE_ENABLED`、`VITE_CODE_TAPE_SUBTITLE_ANCHORS_ENABLED`。关闭事件面板保留旧进度条，关闭代码 anchor 保留字幕时间跳转，关闭协作保留本地录制；任何开关都不能关闭服务端账号和资产鉴权。

API 的仓库根目录 `.env.local` 不会自动成为 Vite 配置。前端开关应放在 `apps/web/.env.local`，或通过构建进程环境显式传入，例如 `VITE_CODE_TAPE_COLLABORATION_ENABLED=false npm run build -w apps/web`；修改后需要重新部署 Web 构建，不是只重启 API。服务器密钥不能使用 `VITE_` 前缀，前端配置不是秘密。

前端诊断日志默认关闭，只有以 `VITE_CODE_TAPE_DEBUG_ENABLED=true` 构建时才输出结构化 `console.debug`。日志使用固定阶段/结果与白名单数值、规范标识符，覆盖回放 load/seek 世代、观察流缺口与快照、协同持久化阶段，不记录源码、字幕、URL 或凭据。`send-called` 只表示调用发送成功，不证明服务端收到；判断落盘应看持久化 ACK。正式性能测量保持诊断日志关闭。

## 6. 可复现的恢复演练

先构建 Schema 和 API，再运行独立脚本测试：

```sh
npm run build:api
node --test scripts/tests/data-backup.test.mjs
```

测试只使用临时目录、临时账号和合成私有对象，不接触用户数据。它真实注册账号、保存受保护资产与数据库记录，关闭服务，执行备份/验证/新目录恢复，再启动真实 Runtime 验证 `auth/me`、私有 HTTP 资产字节和 Range。另覆盖损坏备份拒绝、已有目标拒绝、祖孙路径拒绝、符号链接与路径穿越拒绝。

演练通过证明工具可以恢复这一完整样本，不代表已建立生产备份 SLA，也不能替代首次上线前在目标部署环境中的恢复演练。上线记录应保存具体版本、快照时间、外部密钥版本、验证结果和切换记录；备份频率与保留期根据真实录制量和可接受的数据丢失窗口另定。
